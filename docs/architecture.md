# 시스템 구조

## 데이터 흐름

```
입고            발주(PO)                     출고
──────         ──────────                  ──────
S/N 범위    →   출고요청 (차수별)        →   출고확정
등록            └ 출고요청상세 (품목별)      └ 출고이력 (실제 나간 것)
                   └ 출고배정 (S/N 범위)
                        │
                        ▼
                  패킹리스트 (문서)
                   └ 패킹리스트행 (카톤별)
```

각 단계가 **되돌릴 수 있어야** 합니다. 출고를 확정했다가 취소하고, 수량을 줄여
다시 확정하는 일이 실무에서 일어납니다. 그래서 어느 단계도 데이터를 지우지 않고
상태로 표시합니다.

---

## 왜 상태를 지우지 않는가

| 상황 | 지웠다면 | 지금 |
|---|---|---|
| 출고 취소 | 무엇이 나갔었는지 모름 | `취소여부` 표시, 이력 보존 |
| 카톤 합침 | 원래 몇 개였는지 모름 | 수량 0 + `정정잉여` 표시 |
| 문서 값 수정 | 왜 바뀌었는지 모름 | 변경 전후값을 이력에 기록 |

실제로 이 덕을 봤습니다. 어떤 박스 규격이 `195mm → 195 → 195mm` 로 왕복한 적이
있는데, 양쪽 변경이 다 이력에 남아 있어서 **자동 반영이 사람의 이전 정정을
되돌렸다**는 걸 짚어낼 수 있었습니다. 이력이 없었으면 영영 몰랐을 것입니다.

대가는 [`src/row_status.py`](../src/row_status.py) 에 적었습니다 —
읽는 쪽이 전부 걸러야 하고, 한 군데만 빠뜨려도 조용히 틀립니다.

## 검증 계층

배포 전에 세 겹을 통과해야 합니다.

```
① 통합검증    실제 흐름을 처음부터 끝까지 태운다
              (입고 → 예약 → PL 생성 → 확정 → 출고 → 취소 → 원복)
              일회용 DB 를 만들어 돌리고 지운다

② 회귀        고쳤던 버그가 되살아나지 않는지
              각 검사에 "왜 이걸 보는가" 를 문서로 적는다

③ 정적 검사    화면 JS 구문 · 캐시 무효화 · CSS 변수 존재 여부
```

### ③ 이 왜 필요했나

한 번은 JS 를 고치고 캐시 무효화 값을 안 올려서, **브라우저가 옛 코드를 계속 쓰는
상태**로 배포했습니다. 백엔드는 새 응답 형식인데 화면은 옛 형식을 읽어서,
에러 없이 **조용히 틀린 화면**이 떴습니다.

또 한 번은 `var(--warn, #c60)` 처럼 **존재하지 않는 CSS 변수**를 썼습니다.
fallback 이 있으니 에러도 없고 화면도 뜨는데, 테마 색이 아니라 하드코딩 색이
나갑니다. 다크 배경에서 안 보였습니다. 검사를 붙이자 같은 문제 2건이 더 나왔습니다.

둘 다 **"통과했는데 틀린" 부류**라, 사람이 눈으로 보는 것으로는 못 막습니다.

## 두 대의 PC 로 교차검증

작업 PC 에서 고치고, 서버 PC 가 반증합니다.

```
작업 PC  →  "이렇게 고쳤다. 근거는 이것이다"
서버 PC  →  코드를 직접 열어 반증 시도
            "그 전제가 틀렸다" 또는 "확인했다"
```

동의를 구하는 게 아니라 **깨보라고** 넘기는 게 요점입니다.
실제로 여러 번 결론이 뒤집혔고, 그중 하나가
[분할출고 잔여 계산](split-shipment.md) 건입니다.

반대로 제가 서버 쪽 보고를 확인 없이 받아들여 틀린 적도 있습니다.
"이미 반영했다" 는 보고를 전제로 코드를 뒤집었는데, 그 반영은 이미 되돌려져
있었습니다. **양쪽 다 재봐야 한다**는 게 결론입니다.

## 기술 선택

| | | 이유 |
|---|---|---|
| 백엔드 | Python 표준 라이브러리 위주 | 사내 PC 에 설치·이전이 단순해야 함 |
| 프런트 | 바닐라 JS | 빌드 도구 없이 파일만 복사하면 도는 구조 |
| DB | PostgreSQL | 동시 접근·트랜잭션. 초기엔 SQLite 였고 어댑터로 전환 |
| 엑셀 | openpyxl | 패킹리스트가 결국 엑셀로 나가야 함 |

프레임워크를 안 쓴 건 취향이 아니라 제약이었습니다. 사내 PC 에서 돌아야 했고,
제가 없을 때 다른 사람이 실행할 수 있어야 했습니다.

한글 식별자(`출고요청`, `남은수량`)를 그대로 쓴 것도 같은 이유입니다.
업무 용어와 코드 용어가 다르면 물류 담당자가 코드를 못 읽습니다.
