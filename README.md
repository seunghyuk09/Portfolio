# 물류 입출고 · 시리얼번호 관리 시스템

> 중소 제조사의 수출입 물류를 엑셀 수기 작업에서 웹 시스템으로 옮긴 사내 프로젝트입니다.
> 물류 담당자로 일하면서 직접 설계하고 만들었고, 지금 회사에서 실제로 돌아갑니다.

이 저장소는 **포트폴리오용 공개본**입니다. 사내 코드에는 고객사·발주번호·품목코드가
얽혀 있어 그대로 공개할 수 없어, **로직과 설계 판단만 남기고 가상의 데이터로 다시
썼습니다.** 아래 코드는 전부 실제 시스템에서 풀었던 문제를 재현한 것입니다.

---

## 무엇을 푸는 시스템인가

제품 하나하나에 **시리얼 번호(S/N)** 가 붙는 하드웨어를 수출합니다.
발주(PO)가 들어오면 재고에서 S/N 을 잡아 포장하고, 박스마다 무엇이 몇 개
들었는지 적은 **패킹리스트(Packing List)** 를 만들어 고객과 세관에 보냅니다.

수기로 할 때의 문제는 이랬습니다.

| | |
|---|---|
| S/N 을 엑셀로 관리 | 어느 번호가 어디로 갔는지 추적이 안 됨. 중복 출고가 남 |
| 패킹리스트를 손으로 작성 | 박스 나누기·무게 계산·번호 범위를 매번 손으로. 오타가 그대로 세관에 감 |
| 부분 출고 | 1,000개 주문 중 400개만 먼저 보내면 남은 수량을 사람이 기억해야 함 |
| 실물과 장부가 어긋남 | 담당자가 문서를 고쳐도 시스템은 모름 |

이 시스템은 **재고 → 배정 → 패킹리스트 → 출고확정** 을 한 줄기로 잇고,
각 단계에서 어긋날 수 있는 것을 검사로 막습니다.

## 도메인에서 어려웠던 것들

포트폴리오로서 봐주셨으면 하는 부분입니다. 흔한 CRUD 가 아니라
**업무 규칙이 지저분한 곳**을 어떻게 정리했는지가 이 프로젝트의 내용입니다.

### ① 시리얼 번호는 '범위' 로 다뤄야 한다

100개를 출고할 때 `SN0001~SN0100` 처럼 **연속 범위**로 적습니다.
그런데 재고는 출고를 거듭하며 조각납니다. 범위를 잘라 쓰고 남은 조각이
쌓이면 패킹리스트가 `SN0001~0040, SN0071~0130` 처럼 지저분해집니다.

→ [`src/serial_allocation.py`](src/serial_allocation.py)
  범위를 자르고, 인접한 조각을 도로 합치고, 요청 수량을 가장 적은 조각 수로 채웁니다.

### ② 부분 출고의 '남은 수량' 을 무엇으로 셀 것인가

1,000개 주문을 400 → 600 으로 나눠 보낼 때, 2차의 잔여는 600 입니다.
그런데 **1차를 확정했다가 취소하고 300 으로 줄여 다시 확정**하면?

실제로 이런 일이 있었습니다. 잔여를 *"주문 − 이전 차수에 **걸어둔** 수량"* 으로
계산하고 있었는데, 취소·축소를 해도 그 '걸어둔 수량' 은 줄지 않았습니다.
화면에는 "1차 실출고 300" 이라고 뜨는데 잔여는 600 으로 계산됐습니다. 100개가 붕 떴습니다.

→ [`src/split_shipment.py`](src/split_shipment.py)
  잔여를 **실제로 나간 출고 이력**에서 셉니다. 화면과 계산이 같은 원천을 봅니다.

이 건은 [설계 문서](docs/split-shipment.md)에 왜 그렇게 판단했는지 적었습니다.
"지금 틀린 데이터는 없지만 경로가 열려 있다" 를 어떻게 확인했는지가 요점입니다.

### ③ 사람이 고친 문서와 시스템 계산이 다를 때

담당자가 패킹리스트를 손으로 다듬어 보내는 일이 있습니다.
그 문서를 다시 시스템에 넣어 "이게 정답이다" 하고 학습시킵니다.
그런데 문서와 DB 가 다르면 **어느 쪽이 진실인가?**

```
DB   4.84   = 단위중량 0.0242 × 200개   (시스템 계산값)
문서  4.8    = 담당자가 반올림해 적은 값
```

둘 다 맞습니다. 성격이 다를 뿐입니다. 반면 이런 것도 있었습니다.

```
DB   570 X 260 X 195mm
문서  570 X 260 X 195      ← 단위가 통째로 빠짐 (문서 쪽 실수)
```

앞은 **사람의 판단**이라 존중해야 하고, 뒤는 **표기 손실**이라 DB 를 깎으면 안 됩니다.
구분하는 규칙을 세우고, 어느 쪽이든 **사람에게 알립니다.**

→ [`src/document_reconcile.py`](src/document_reconcile.py)

### ④ 지우지 않고 표시한다

카톤을 합치면 남는 행이 생깁니다. 지우는 대신 **수량 0 + 상태 표시**로 남깁니다.
출고를 취소해도 이력을 지우지 않고 `취소여부` 를 세웁니다.

되돌릴 수 있고 추적할 수 있게 하려는 것인데, 대신 **읽는 쪽이 전부 그 상태를
걸러야 합니다.** 한 군데라도 빠뜨리면 "행 수가 안 맞는다" 며 엉뚱하게 동작합니다.
실제로 그런 버그를 만들었고, 걸러야 할 상태 목록을 **한 곳에서만 정의**하도록 고쳤습니다.

→ [`src/row_status.py`](src/row_status.py)

## 어떻게 일했는가

코드보다 이쪽이 더 하고 싶은 이야기입니다.

### 검사를 믿지 않는다 — 일부러 망가뜨려 본다

회귀 테스트를 만들면 **그 테스트가 진짜 잡는지** 확인합니다.
코드를 일부러 고장 내고 테스트를 돌려서, 빨간불이 안 뜨면 그 테스트는 장식입니다.

```
[잡음] Gross 를 안 쓴다              → ① 빈칸이던 값이 채워진다
[잡음] 구성 가드를 없앤다             → ③ 카톤 수가 다르면 안 고친다
[놓침] 자릿수 비교를 뺀다             ← 검사 구멍? 아니면 조건이 중복?
```

실제로 이 방식으로 **"통과하는데 아무것도 검사하지 않는 테스트"** 를 여러 번 잡았습니다.
한 번은 정규식이 깨져 아무것도 매치하지 않는데 초록불이 뜨고 있었습니다.

→ [`tests/mutation_check.py`](tests/mutation_check.py) — 돌연변이 검사 하네스

### 두 대의 PC 가 서로 반증한다

작업 PC 에서 고치면 서버 PC 가 **반증을 시도**합니다. 동의를 구하는 게 아니라
"이 주장을 코드로 깨보라" 고 넘깁니다.

이 절차가 실제로 값을 했습니다. 위 ② 건에서 저는 *"취소하면 그 차수가 계산에서
빠지니 문제가 생길 수 없다"* 고 결론냈는데, 서버 쪽이 **되돌아오는 경로**
(취소 → 축소 → 재생성 → 재확정)를 찾아 반증했습니다. 제 결론이 틀렸습니다.

### 손으로 풀지 않는다 — 기능으로 만든다

DB 를 직접 고쳐 해결하고 싶은 유혹이 늘 있습니다. 하지만 그러면
**다른 담당자는 같은 상황에서 아무것도 못 합니다.**

부분 출고 잔여 배정도 처음엔 제가 데이터를 직접 넣어 해결하려 했는데,
그건 시스템이 아니라 제 손기술이었습니다. 이전 출고 이력을 화면에 보여주고
잔여 수량을 골라 배정하는 **기능**으로 다시 만들었습니다.

### 배포는 게이트를 통과해야 한다

```
통합검증 24단계 + 회귀 31종 + JS 구문검사 35개 → 전부 통과해야 push
```

한 번은 이 게이트를 건너뛰고 직접 push 했다가, 캐시 무효화를 빼먹어
**화면이 조용히 옛 코드로 도는** 상태를 배포했습니다. 게이트가 헐거운 게 아니라
게이트를 안 쓴 것이었습니다.

| 기간 | 2025년 ~ 진행 중 (실사용) |

### 왜 프레임워크를 쓰지 않았나

웹 서버는 파이썬에 딸려오는 `http.server` 로 세웠고, 화면은 바닐라 JS 입니다.
외부 라이브러리는 꼭 필요한 것만 썼습니다 — 엑셀(`openpyxl`), DB 드라이버(`psycopg`).

Django 나 FastAPI 를 얹으면 개발은 편해지지만, **설치할 것이 늘고 배포가 그만큼
무거워집니다.** 이 시스템의 제약은 두 가지였습니다.

- 사내 PC 에서 돌아야 한다 — 인터넷이 막힌 자리도 있다
- **내가 없을 때 다른 사람이 실행할 수 있어야 한다**

두 번째가 결정적이었습니다. 파일을 복사하고 `.bat` 하나 누르면 도는 구조여야 했습니다.
프레임워크를 안 쓴 건 몰라서가 아니라 **이 제약에서 그게 손해였기 때문**입니다.

동시 사용자가 늘거나 서버를 여러 대로 나눠야 하는 규모가 되면 그때는 프레임워크가
맞다고 봅니다. 지금은 사내 소수가 쓰는 규모라 그 비용이 이득보다 큽니다.
